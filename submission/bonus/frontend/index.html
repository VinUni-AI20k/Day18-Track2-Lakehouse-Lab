§4 — Failure Modes

3 AM Scenarios Tied to Day 18 Concepts

1 False-Negative Dedup — Fraud Ring Escapes Detection RESTORE + time travel

A bug causes two events with different event_id but identical receipt_hash to both be marked is_duplicate=false. The fraud ring exploits this with distinct UUIDs per event.

Detection

  • Daily reconciliation: COUNT(*) WHERE receipt_hash IN (GROUP BY receipt_hash HAVING COUNT(*)>1) should match is_duplicate=true count
  • Discrepancy → PagerDuty alert

Rollback (Day 18)

RESTORE TABLE silver.player_events_dedup VERSION AS OF 46 — Delta history() shows which version introduced the bug. event_id UUIDs preserved as audit trail.

2 Salt Rotation Breaks Player Identity Continuity VERSION AS OF + GDPR

Quarterly salt rotation makes SHA-256(player_id || old_salt) != SHA-256(player_id || new_salt). Cross-epoch joins for fraud investigation fail.

Detection

  • Alert if DATEDIFF(CURRENT_DATE, MAX(salt_date)) > 90
  • Old salt retained in Secrets Manager for 365 days post-rotation

Rollback (Day 18)

Delta time travel via VERSION AS OF preserves table state at each salt epoch. player_dim_scd2 records which salt was active at effective_from. For GDPR erasure: old salt re-identifies + hard-deletes player's raw data before new salt is applied.

3 Late-Arrival Reorders Fraud Signals After Gold Runs TIMESTAMP AS OF + MERGE

A currency duping event arrives 7 minutes after the Gold batch completes. The 5-min fraud score misses the player, creating a false negative — no account freeze.

Detection

  • Late-arrival watermark audit log tracks which 5-min windows had late events arrive post-Gold-run
  • If late events > threshold → Gold job re-triggered for that window only

Rollback (Day 18)

No data rollback. TIMESTAMP AS OF lets fraud analyst query Silver at the exact arrival time, not event time — critical for post-incident review. Late event incorporated in next Gold run. Fraud team notified via PagerDuty if account was already frozen.

Two Fraud Patterns Injected

Receipt Double-SpendIAP Exploit

Fraudsters submit the same receipt_hash twice with different currency_delta values — distinct event_id UUIDs bypass simple dedup, but receipt collision reveals the exploit in Gold.

Detection: GROUP BY receipt_hash HAVING COUNT(*)>1
Idle Reward SpamCurrency Amplification

Rapid-fire idle_reward events (<1s apart) exploit a timing bug in the server-side reward cooldown. 10 duping players × 10 rapid events each = 90 spam alerts.

Detection: WHERE ts - LAG(ts) < 1s per player

§6 — Week-1 MVP Slice

Smallest Shippable Cut

1
Synthetic Event Generator
50K events/day with realistic event_type distribution (40% click, 30% idle_reward, 3% IAP, etc.) + fraud pattern injection. RNG seeded for reproducibility.
2
Bronze Landing — tokenize_player()
SHA-256(player_id + daily_salt) written to Delta Bronze. Raw PII never touches disk. Salt rotates daily. All Bronze fields: event_id, player_id_enc, device_id_enc, session_id, event_type, currency_delta, ts, receipt_hash, game_version, platform, salt_date.
3
Silver Dedup — dedup_silver()
MERGE on event_id with WHEN MATCHED AND src.ts > tgt.ts for late-arrival handling. is_duplicate and late_arrival_flag columns added. Demonstrates Delta MERGE semantics.
4
Gold Fraud Metric — duped_currency_alert
Rule-based detection: receipt_hash collisions (GROUP BY HAVING COUNT>1) + idle reward spam (<1s interval). Rule-based is sufficient for MVP; ML scoring comes in Phase 2.

What Is NOT in MVP

Full CDC pipeline (Kafka + Debezium) — replaced with batch synthetic writer Player dimension SCD2 — flat attributes only ML-based fraud scoring — rule-based for MVP Storage tiering — all S3 Standard Polaris catalog — local filesystem Delta for demo
