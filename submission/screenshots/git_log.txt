    Add a native Apple `container` runner for the Spark path
    
    Apple's `container` cannot run docker-compose.yml: there is no compose
    plugin (`container compose` -> "Plugin 'container-compose' not found") and
    no Docker API socket, so neither `docker` nor `docker compose` can drive
    it. scripts/apple_container.sh brings up the same three-service stack with
    plain `container run`.
    
    The compose file is UNCHANGED and remains the primary Spark path. These
    are two parallel options; use whichever runtime you have.
    
      make apple-up / apple-smoke / apple-data / apple-status / apple-down / apple-clean
    
    The one architectural difference: compose resolves the service name `minio`
    over its built-in DNS. Apple's runtime has no name resolution unless you
    create a DNS domain, and `container system dns create` needs sudo. Rather
    than ask for root, the script reads MinIO's IP from `container inspect` and
    injects it as MINIO_ENDPOINT. spark_session.py now honours MINIO_ENDPOINT /
    MINIO_ROOT_USER / MINIO_ROOT_PASSWORD, defaulting to http://minio:9000 and
    minioadmin — so the compose path is provably unchanged (MINIO_ENDPOINT
    appears 0 times in docker-compose.yml).
    
    Things this runtime does differently, learned by running it:
    
      - It defaults to 1 GB / 4 CPUs per container, and Spark at 1 GB thrashes
        until the guest stops answering `container exec` at all — `container
        list` still responds, so it presents as a hang rather than an OOM. The
        1M-row generate_data job is the step that triggers it. The script now
        passes -c 4 -m 6g for Spark and -c 2 -m 2g for MinIO, overridable via
        SPARK_MEM / SPARK_CPUS.
      - Jupyter announcing "is running at" does NOT mean the stack is usable:
        `pip install --user` is still running, so a smoke test fired right after
        `up` fails with "No module named 'delta'". `up` now waits for
        `import delta, pyspark` to succeed and FAILS LOUDLY if it never does,
        instead of printing "Stack is up" over a half-built stack.
      - `container list -a --format json` is matched on configuration.id
        exactly; a raw grep would also hit image names and digests, and the
        host may have unrelated containers that must never be touched.
      - Colour output is gated on a TTY so escape codes stay out of logs.
    
    Bind mounts are writable by uid 1000 here, and the image's PYTHONPATH still
    has to be extended rather than replaced — the same trap that broke compose.
    
    Verified end-to-end on Apple `container` 1.2.2 (macOS 26.5.1, arm64):
      up (with the new readiness gates) ok
      scripts/verify.py green — Spark -> MinIO (S3A) -> Delta -> time travel
      generate_data.py wrote 1,000,000 rows to s3a://bronze
      notebooks-spark 4/4 pass
      notebooks (lightweight) 8/8 pass in the container
    
    Host lightweight path unaffected: smoke, 24 pytest, 8/8 run-all.

    Fix the Spark path: 4 pre-existing bugs that made it fail to start
    
    Booted Docker for this lab for the first time (lima + rootless Docker) and
    `make spark-up` never worked on a modern Docker Compose. Four independent
    faults, all pre-existing — verified against the pre-change compose file,
    which fails identically:
    
    1. Compose interpolation. `${f%.py}` in the `command:` block is shell
       parameter expansion; Compose reads it as a variable and aborts with
       "invalid interpolation format", so the stack never came up. Literal
       dollars must be doubled — including inside comment lines, because
       Compose interpolates the whole block, comments and all.
    
    2. jupytext not on PATH (exit 127). `pip install --user` puts console
       scripts in ~/.local/bin, which this image does not have on PATH, so
       `jupytext` died with 127 and `set -e` killed the container before
       Jupyter started. Now invoked as `python -m jupytext`, and ~/.local/bin
       is exported for interactive shells.
    
    3. PYTHONPATH was clobbered. The pyspark-notebook image exposes pyspark
       *only* through PYTHONPATH (spark/python + the py4j zip, set by its
       10spark-config.sh hook). `environment: PYTHONPATH: /workspace/scripts`
       replaced it, so `import pyspark` failed in every notebook and in
       scripts/verify.py — the entire Spark path was dead. Now composed with
       the image's own entries, and set at container level so
       `docker compose exec` (i.e. `make spark-smoke`) inherits it too; the
       image hook only runs for the main process.
    
    4. Ivy cache unwritable → JAVA_GATEWAY_EXITED. The named volume mounted at
       ~/.ivy2 is created root-owned, because that path does not exist in the
       image, so Ivy could not write its resolution file and the JVM exited
       before the Py4J gateway came up. ~/.cache does exist in the image, so
       its volume inherits jovyan ownership: spark.jars.ivy now points at
       ~/.cache/ivy via SPARK_IVY_DIR, and the broken volume is removed.
    
    Also: .py→.ipynb conversion is now best-effort. On a native-Linux host
    whose UID is not 1000 the bind mount is not writable by jovyan, and that
    previously killed the container; it now logs a warning and Jupyter starts
    anyway.
    
    The container additionally installs the lightweight stack, so all twelve
    notebooks run there, not just the four PySpark ones.
    
    Verified end-to-end in Docker, not just syntax-checked:
      - scripts/verify.py green: Spark boots with Delta, writes to MinIO over
        S3A, reads back, time-travels, DESCRIBE HISTORY
      - generate_data.py wrote 1,000,000 rows to s3a://bronze
      - 4/4 notebooks-spark and 8/8 lightweight notebooks pass in the container
    
    Lightweight path unchanged and still green (smoke, 24 pytest, 8/8 run-all).
